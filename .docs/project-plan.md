자연어로 입력한 투자 조건을 AI가 실행 가능한 전략 파라미터로 변환하고, 국내 주식 시세를 이용한 백테스트와 페이퍼 트레이딩으로 검증하는 웹 서비스를 개발한다. 사용자는 전략을 코드로 작성하지 않고도 전략을 만들고, 결과를 이해하고, 여러 전략의 성과를 비교할 수 있어야 한다.

## 2. 프로젝트 개요와 개발 배경

### 2.1 프로젝트명과 주제

**프로젝트명:** 프롬프트 기반 자동매매 전략 생성 및 백테스트 플랫폼

**프로젝트 주제:** 자연어로 입력한 투자 조건을 AI가 해석하여 자동매매 전략 파라미터로 변환하고, 이를 바로 백테스트·모의투자로 검증해주는 웹 서비스.

### 2.2 해결하려는 문제

원문은 개인 투자자 증가와 AI 기반 투자 앱·자동매매에 대한 관심 확대를 배경으로 제시한다. 한국예탁결제원의 결산 상장법인 주식 소유자 현황을 인용하여 2025년 12월 개인 투자자 수를 약 1,455만 명으로 설명한다.

규칙 기반 자동매매에서는 투자 조건을 바꾸기 위해 코드를 수정하고 다시 배포해야 하는 경우가 있어 새로운 아이디어를 빠르게 실험하기 어렵다. 프로그래밍에 익숙하지 않은 사용자는 투자 아이디어를 코드로 표현하는 단계부터 진입장벽을 겪는다.

본 프로젝트는 자연어 인터페이스로 이러한 장벽을 낮춘다. 사용자가 매수·매도 조건을 문장으로 입력하면 AI가 백테스트 엔진에서 사용할 파라미터로 변환한다. 실행 결과는 수치와 함께 자연어 요약으로 제공한다.

### 2.3 원문의 대표 사용 예시

> 이동평균선이 골든크로스 나면 매수하고, 5% 손실이면 손절한다.

이 문장에서 매수 조건과 손절 조건을 추출해 전략으로 표현하고, 과거 시세로 실행한 결과와 전략의 특징을 설명한다. 이동평균선 종류·기간 등 문장에 없는 값은 원문에서 정하지 않았다. 해당 값의 처리 정책은 개발 전에 결정해야 한다.

### 2.4 차별화와 기대 효과

원문은 2026년 7월 두나무가 출시한 것으로 기술한 '업비트 스트래티지 툴킷'을 유사 서비스 사례로 제시한다. 자연어 전략을 규칙으로 변환하고 과거 시세로 검증한다는 방향성을 참고하되, 본 프로젝트는 코스피·코스닥 주식과 페이퍼 트레이딩까지 연결하는 것을 차별점으로 삼는다. 경쟁 서비스의 출시일과 제공 범위는 출처 확인 대상이다.

일반적인 모의투자가 시세에 맞춰 매매를 연습하는 데 초점을 둔다면, 본 프로젝트에서는 사용자가 직접 매매 규칙을 설계하고 그 규칙을 검증한다. 전략의 근거와 시장 데이터를 함께 살펴보는 경험을 제공하여 데이터 기반 투자 판단과 전략 검증에 대한 접근성을 높이는 것이 목표다.

### 2.5 원문 삽입 자료

원문에는 `12월 결산 법인의 실질주주수 추이` 그래프 1개가 포함되어 있다. 가로축은 2009~2025년이며 주요 표시값은 2009년 4,157,975명, 2014년 4,415,830명, 2019년 6,187,021명, 2021년 13,842,667명, 2025년 14,558,479명이다.

## 3. 기획서의 주요 기능

### 3.1 자연어 전략 생성

자연어 프롬프트를 진입 조건, 청산 조건, 손절률, 보유기간 등 전략 파라미터로 변환한다.

### 3.2 백테스트 실행과 성과 산출

변환된 파라미터를 백테스트 엔진에 전달해 실행한다. 수익률, 승률, 샤프비율 등 성과 지표를 산출한다.

### 3.3 AI 결과 요약

백테스트 결과를 사람이 읽기 쉬운 문장으로 요약한다. 어떤 구간에서 왜 수익 또는 손실이 발생했는지 이해할 수 있도록 전략의 성과와 특징을 설명한다.

### 3.4 웹 대시보드

전략 입력, 백테스트 결과 조회, 페이퍼 트레이딩 현황 확인을 웹 화면에서 제공한다.

### 3.5 전략 저장과 비교

여러 전략을 저장하고 성과를 비교한다. 저장한 전략과 결과 이력을 웹에서 조회할 수 있도록 구성한다.

## 4. 기획서의 적용 기술과 구성

- **Backend:** Spring Boot를 이용해 백테스트 엔진과 페이퍼 트레이딩 모듈을 개발하고 API로 제공한다.
- **AI:** LLM API를 사용해 프롬프트를 파싱하고 결과 요약을 생성한다. 제공업체와 모델은 원문에 지정되어 있지 않다.
- **시세 데이터:** FinanceDataReader 기반 코스피·코스닥 데이터로 백테스트와 페이퍼 트레이딩을 구성한다. 일정에는 토스 API 활용도 명시되어 있으므로 과거 데이터와 진행 중 시세의 공급원 역할을 구체화해야 한다.
- **DB:** H2를 사용한다. 추후 개선 가능할 경우 Supabase로 전환하는 방안을 검토한다. 전환은 필수 요구사항이 아니다.
- **Frontend:** 전략 입력 폼, 백테스트 결과 차트, 전략 비교 화면을 중심으로 웹 UI를 구성한다. 특정 프론트엔드 프레임워크는 지정되어 있지 않다.
- **전체 방향:** Spring Boot 기반 실행 엔진 위에 자연어 인터페이스와 웹 대시보드를 연결한다.

## 6. 개발 범위 해석과 사용자 흐름

이 장부터는 원문을 구현 가능한 작업으로 구체화한 제안이다.

### 6.1 핵심 개발 범위

국내 주식 전략을 자연어로 생성하고, 검증된 전략을 저장한 뒤 백테스트와 페이퍼 트레이딩에 사용한다. 결과 지표·거래 기록·AI 설명을 조회하고 저장한 전략끼리 비교하는 흐름을 완성한다.

원문에는 실제 자금을 사용하는 주문 실행, 수익 보장, 해외 주식·암호화폐 지원, 모바일 네이티브 앱, 결제 기능이 필수 기능으로 명시되어 있지 않다. 기존 저장소에 관련 기반 코드가 있더라도 이번 기획서의 필수 범위로 자동 편입하지 않는다. Supabase 전환도 후속 개선 후보로 유지한다.

### 6.2 권장 사용자 흐름

1. 사용자가 투자 조건을 자연어로 입력한다.
2. AI가 지원 가능한 전략 구조로 변환한다.
3. 서버가 구조, 값의 범위, 지원 조건과 필수값을 검증한다.
4. 화면에서 해석된 조건, 기본값과 보완이 필요한 항목을 확인한다.
5. 전략을 저장하고 종목·기간 등 실행 조건을 지정한다.
6. 백테스트를 실행해 지표, 거래 내역과 차트를 확인한다.
7. AI 요약으로 결과와 한계를 확인한다.
8. 저장된 다른 전략과 같은 조건에서 비교한다.
9. 선택한 전략을 페이퍼 트레이딩에 연결하고 가상 포지션과 실행 이력을 확인한다.

## 7. 기능별 개발 요구사항과 확인 기준

### FR-01 자연어 파싱과 전략 검증

- 입력: 자연어 투자 조건.
- 출력 제안: 진입·청산 조건, 손절률, 보유기간, 적용한 기본값, 미해결 항목을 포함하는 구조화된 데이터.
- AI 출력은 서버 검증을 통과한 후 실행에 사용한다.
- 지원하지 않는 지표, 잘못된 수치, 서로 충돌하는 조건을 감지하고 사용자에게 이유를 알린다.
- **확인 기준:** 원문의 골든크로스·5% 손절 예시를 표현하고 실행할 수 있다. 기간 누락이나 미지원 조건을 조용히 다른 전략으로 바꾸지 않는다.

### FR-02 전략 저장과 이력

- 원문 프롬프트, 해석된 파라미터와 전략 이름을 저장한다.
- 결과가 어떤 전략 설정에서 생성되었는지 추적할 수 있도록 실행 시점 설정을 보존한다.
- 저장한 전략 목록과 상세 내용을 다시 조회한다.
- **확인 기준:** 전략 수정 후에도 이전 실행의 설정과 결과를 구분할 수 있다. 저장 데이터의 재시작 후 유지 정책을 검증한다.

### FR-03 사용자 전략 백테스트

- 저장하거나 검증한 전략을 기존 엔진에 전달할 수 있는 실행 경로를 제공한다.
- 실행 종목, 데이터 기간, 실행에 사용한 전략 설정을 결과와 연결한다.
- 수익률, 승률, 샤프비율을 제공하고 각 지표의 계산 기준을 명시한다.
- 거래 내역과 차트에 필요한 데이터를 함께 제공한다.
- **확인 기준:** 같은 전략·데이터·실행 조건에서 같은 결과를 얻고, 거래가 없는 경우와 데이터가 부족한 경우를 구분해 표시한다.

### FR-04 결과 설명 생성

- AI에 실제 계산된 지표, 거래 기록, 기간별 성과와 청산 사유 등 확인 가능한 근거를 전달한다.
- 특정 구간의 손익 설명을 제공하려면 그 구간의 데이터가 필요하다. 전체 평균 지표만으로 구간별 설명을 생성하지 않는다.
- 데이터에 없는 뉴스나 시장 사건을 손익의 원인으로 만들어내지 않는다.
- **확인 기준:** 요약의 수치와 거래 설명이 실행 결과에 부합한다. LLM 호출이 실패해도 백테스트 수치 결과는 조회할 수 있다.

### FR-05 전략 비교

- 저장된 여러 전략의 성과를 함께 조회한다.
- 비교 시 종목군, 기간, 초기 자금과 비용 등 비교 조건을 일치시키거나 차이를 표시한다.
- 기존 베이스라인과 최적값 비교 외에 사용자 전략끼리 비교할 수 있어야 한다.
- **확인 기준:** 최소 두 개의 저장 전략을 선택해 설정과 결과를 구분해서 확인할 수 있다.

### FR-06 페이퍼 트레이딩

- 선택한 전략으로 실제 시세를 반영한 가상 매매를 수행한다.
- 전략별 가상 포지션, 청산 기록, 실행 로그와 성과를 조회한다.
- 전략 변경이 이미 실행 중인 모의매매에 어떻게 반영되는지 정책을 정한다.
- **확인 기준:** 백테스트에서 선택한 전략과 모의매매에 적용된 전략을 연결해 확인할 수 있으며, 여러 전략의 포지션이 섞이지 않는다.

### FR-07 웹 화면

- 자연어 전략 입력 및 해석 결과 확인 화면.
- 저장된 전략 목록과 상세 화면.
- 백테스트 실행 조건 입력과 결과 차트·지표·AI 요약 화면.
- 전략 비교 화면.
- 페이퍼 트레이딩 포지션·거래 이력·실행 상태 화면.
- **확인 기준:** 사용자가 별도 API 도구 없이 핵심 흐름을 끝까지 수행할 수 있다. 로딩·실패·빈 결과 상태도 표시한다.

## 8. 전략 표현과 엔진 연결 시 중요한 결정

### 8.1 기존 점수제와 자연어 조건의 차이

현재 `BacktestParams`는 거래대금 필터, 갭상승·급등 필터, 조건별 가중치, 매수 점수 임계값, 손절과 보유기간 등의 필드를 가진다. 이는 기존 단타 규칙의 파라미터화에 적합한 구조다.

그러나 '골든크로스면 매수'라는 단일 조건과 '여러 조건의 합산 점수가 임계값 이상이면 매수'는 서로 다른 전략이다. 손절률만 바꿀 수 있다고 해서 원문의 자연어 전략 요구사항을 모두 지원한다고 볼 수 없다.

**결정할 사항:** 첫 버전이 기존 점수제 전략의 숫자 조정만 지원할지, 지표와 논리 조건을 조합하는 전략 표현까지 지원할지 정한다. 제한된 범위로 시작하더라도 원문 대표 예시를 충족하는지 확인하고 UI에 지원 범위를 명시한다.

### 8.2 권장 구조

- 자연어 입력을 받는 계층과 실행 엔진의 전략 표현을 분리한다.
- 지원 지표·연산자·조건만 포함하는 구조화된 전략 명세를 정의한다.
- 서버에서 검증한 명세를 실행 엔진에 전달한다.
- 기존 점수제 전략은 재사용 가능한 기본 전략 후보로 유지한다.
- LLM이 생성한 임의 Java·Python 코드를 실행하는 방식은 기획서의 파라미터 변환 요구에 필요하지 않다.

### 8.3 수치와 시간의 표현

- 예시의 '5% 손실'을 어떤 부호와 단위로 저장할지 통일한다. 현재 `stopLossRate`는 `-0.05`와 같은 음수 비율을 사용하는 구조다.
- 이동평균선의 종류와 단기·장기 기간을 구분한다.
- 보유기간의 거래일·달력일 기준을 구분한다.
- 조건 미입력 시 기본값 적용 여부와 사용자 확인 방식을 정한다.
- 전략 표현의 버전을 보존해 변경 전후 실행 결과를 추적한다.

## 9. 데이터와 성과 지표 설계 제안

### 9.1 보존할 정보

- 전략: 이름, 원문 프롬프트, 정규화된 명세, 버전, 생성·수정 시각.
- 백테스트 실행: 전략 버전, 종목군, 기간, 데이터 기준, 실행 설정, 상태, 지표와 오류 정보.
- 거래 기록: 종목, 진입·청산 시각과 가격, 수량, 손익, 진입·청산 근거.
- 결과 설명: 연결된 실행, 생성 상태, 요약 내용과 생성 시각.
- 페이퍼 트레이딩: 적용 전략 버전, 가상 자산·포지션, 실행 로그와 거래 기록.

이 항목은 개념 설계 제안이다. 엔티티 이름, 테이블과 API 계약은 구현 단계에서 확정한다.

### 9.2 실행 결과의 해석 기준

수익률의 단순 합산·복리·계좌 수익률 구분, 샤프비율의 수익률 주기와 연율화 여부, 최대 낙폭의 기준 곡선을 명확히 정한다. 초기 자금, 매수 비중, 수수료·세금·슬리피지, 체결 가격과 같은 실행 가정도 결과와 함께 보존하는 것을 권장한다.

현재 코드는 거래 수익률의 단순 합산 누적수익률, 거래별 평균/표준편차에 기반한 비연율화 샤프 근사치, 거래 순서의 누적수익률 곡선에서 구한 낙폭을 사용한다. 화면과 AI 설명에서 이를 일반적인 계좌 자산곡선 지표로 오인하지 않도록 해야 한다.

### 9.3 데이터 점검

FinanceDataReader 과거 시세와 토스 API 시세의 역할, 지원 봉 주기, 종목 코드, 시간대, 수정주가 사용 여부를 정한다. 데이터 누락·중복·정렬과 지표 계산에 필요한 준비 기간을 검증한다. 미래 데이터를 매매 판단에 사용하는지와 당일 미완성 봉의 처리도 점검한다.

## 10. 품질과 실패 처리 제안

- LLM 응답 형식 오류·시간 초과·실패를 사용자에게 구분해 안내한다.
- 잘못된 전략 명세는 엔진 실행 전에 차단한다.
- 실행 실패도 상태와 이유를 기록해 재조회할 수 있게 한다.
- 오래 걸리는 백테스트의 동기·비동기 실행 방식을 정하고 화면에서 진행 상태를 표현한다.
- 같은 모의매매 실행이 중복 호출될 때 포지션 중복 생성 방지 방식을 검토한다.
- API 키는 전략 데이터나 화면 응답에 포함하지 않는다.
- 다중 사용자 서비스가 필요하다면 전략과 결과의 소유권·조회 범위를 별도로 설계한다. 로그인 요구는 원문에서 확정되지 않았다.

## 11. 현재 저장소와 기획서의 연결점

2026-09-07에 파일 목록, 빌드 설정, 주요 컨트롤러, 파라미터·결과 클래스, 데이터 수집 스크립트 및 화면 관련 검색으로 확인한 내용이다. 아래 '존재'는 운영 정상 동작이나 기능 완성을 보장하지 않는다.

### 11.1 재사용할 기반

- `build.gradle`: Java 17, Spring Boot 3.5.15, JPA, Security, Web, WebFlux, H2 의존성.
- `backtest/`: 엔진, 파라미터, 그리드서치, 결과 집계, 캔들 저장·수집·CSV 적재 코드.
- `paper/`: 모의매매 서비스, 스케줄러, 포지션과 실행 로그 저장·조회 코드.
- `signal/`: 기술 지표 계산과 매매 신호 관련 코드.
- `client/`, `oauth/`, `marketdata/`: 토스 API 클라이언트, 인증과 시세 관련 코드.
- `scripts/fetch_candles.py`: FinanceDataReader로 코스피·코스닥 각각 시가총액 상위 100개를 후보로 선정해 캔들을 CSV로 수집하는 코드. 실제 수집 결과는 별도 확인 대상이다.
- `src/main/resources/static/`: 기존 HTML·JavaScript·CSS 대시보드.

위 패키지 경로의 기준은 `src/main/java/com/tossinvest/tossinvestbackend/`이다.

### 11.2 확인한 기존 API

- `POST /api/backtest/import-csv`: CSV 캔들 적재.
- `POST /api/backtest/collect`: 토스 API 캔들 수집.
- `GET /api/backtest/candle-status`: 종목별 저장 캔들 수 조회.
- `POST /api/backtest/run`: 전체 그리드서치 실행.
- `GET /api/backtest/run-baseline`: 단일 종목의 기본값 실행.
- `GET /api/backtest/run-optimal`: 단일 종목의 정해진 최적값 실행.
- `GET /api/backtest/compare`: 베이스라인과 정해진 최적값 비교.
- `POST /api/paper/run`: 모의매매 수동 실행.
- `GET /api/paper/summary`, `/positions`, `/history`, `/logs`: 모의매매 요약·포지션·이력·로그 조회.
- `POST /api/paper/close/{id}`: 가상 포지션 수동 청산.

확인한 백테스트 컨트롤러에는 사용자 전략 명세를 요청 본문으로 받아 실행하는 경로가 없다. 모의매매 컨트롤러에도 전략 ID를 선택하는 인터페이스가 없다. 기획서대로 연결하려면 이 부분의 확장 설계가 필요하다.

### 11.3 신규 개발 또는 추가 확인 대상

- 자연어 전략 파싱과 LLM 연동 계층.
- 전략 명세 검증과 엔진 연결.
- 사용자 전략 저장·버전 관리·결과 이력.
- 실행 결과 기반 AI 설명 생성.
- 사용자 전략을 선택하는 비교 기능.
- 전략별 페이퍼 트레이딩 연결과 상태 분리.
- 자연어 입력부터 실행 결과까지 연결하는 화면.

파일 목록과 확인 범위에서 이 기능들을 완성된 것으로 확인하지 못했다. 기존 백테스트·대시보드가 존재한다는 이유로 기획서 기능이 완료되었다고 표시하지 않는다.

### 11.4 기존 문서와의 관계

[trading-rules.md](trading-rules.md)는 특정 단타 전략의 지표·점수·손절·청산 규칙과 검증 기록을 담고 있다. 이 문서는 플랫폼 전체 기획이 아니라 기본 전략 후보와 기존 엔진 동작을 이해하기 위한 자료로 사용한다.

기존 문서의 실거래 확장 방향, 스캘핑 및 해외 종목 관련 내용은 이번 제출 기획서의 필수 범위와 구분한다. 두 문서의 수치를 자동 통합하거나 기존 규칙을 임의로 변경하지 않는다.

## 12. 권장 개발 순서

1. **전략 표현 범위 확정:** 지원할 지표·조건·단위·기본값과 원문 대표 예시의 실행 방식을 정한다.
2. **엔진 계약 정리:** 임의의 검증된 전략을 백테스트에 전달하는 구조와 지표 계산 기준을 정한다.
3. **전략과 실행 결과 저장:** 전략 버전과 실행 당시 설정을 보존하고 재조회 경로를 만든다.
4. **자연어 변환 연결:** LLM 변환, 서버 검증, 해석 결과 확인을 연결한다.
5. **단일 전략 전체 흐름 완성:** 자연어 입력 → 저장 → 백테스트 → 결과 조회를 먼저 완성한다.
6. **AI 요약과 비교:** 실제 거래 근거에 따른 요약과 동일 조건의 복수 전략 비교를 추가한다.
7. **전략별 모의매매 연결:** 선택한 전략으로 가상 매매를 수행하고 결과를 구분한다.
8. **통합 점검과 시연:** 정상·오류 시나리오를 검증하고 발표 자료를 준비한다.

이 순서는 의존관계에 따른 제안이며, 제출 기획서의 월별 일정을 대체하지 않는다. 기존 코드는 재사용 가능성을 먼저 확인한다.

## 13. 개발 전에 결정할 사항

- 첫 버전의 전략 범위는 기존 점수제 조정인가, 지표별 조건 조합까지인가?
- 골든크로스의 이동평균 종류와 기간 등 누락값을 기본값으로 처리할 것인가, 재입력받을 것인가?
- LLM 제공업체·모델, 응답 형식, 비용과 호출 제한은 무엇인가?
- 최초 지원 봉 주기와 시세 갱신 주기는 무엇인가?
- FinanceDataReader와 토스 API의 역할을 어떻게 나눌 것인가?
- 백테스트의 자금·체결·비용·성과 지표 기준은 무엇인가?
- 단일 사용자 시연용인가, 회원별 전략을 분리하는 서비스인가?
- H2의 저장 방식과 재시작 후 이력 보존 정책은 무엇인가?
- 페이퍼 트레이딩의 전략 선택·변경·시작·중지 정책은 무엇인가?
- 프론트엔드는 기존 정적 화면을 확장할 것인가, 별도 구성이 필요한가?
- Supabase 전환은 이번 학기 범위에 포함할 것인가? 원문상으로는 선택 개선 사항이다.
- 원문의 개인 투자자 통계와 경쟁 서비스 설명의 정확한 출처는 무엇인가?

## 16. 사용자 전략 엔진 연결 진행 기록 (2026-09-09)

11장의 내용은 2026-09-07 조사 당시 기록이다. 이후 1단계 [기존 엔진 검증](engine-validation.md)과 [사용자 전략 명세](strategy-spec.md)를 바탕으로 사용자가 지정한 3단계, 사용자 전략을 백테스트 엔진에 연결하는 기능을 구현했다.

- `POST /api/backtest/run-strategy`: 전략 명세·종목·기간·체결 방식을 받아 저장된 일봉으로 실행한다.
- 이동평균 교차(SMA/EMA), SIMPLE RSI, 직전 평균 대비 거래량과 한 단계 AND/OR, 선택한 손절·익절·시간 청산·트레일링을 지원한다.
- 조건의 필수값 누락과 미지원 입력을 서버에서 검증한다. 기존 점수제 필터를 사용자 전략에 추가하지 않는다.
- 종가·다음 시가 방식을 구분하고 진입·청산의 신호/체결 시각과 실제 조건 근거를 반환한다.
- 보유 포지션의 미실현 손익과 마지막 미체결 신호를 완료 거래 통계에서 분리한다.
- 전략 판단은 DB·주문과 독립적인 `StrategyEvaluator`로 구성해 이후 모의매매에서 재사용할 수 있도록 했다.
- 기존 베이스라인·그리드서치 API와 엔진은 유지한다. 결과는 현재 거래 단위·비용 미반영 성과이며 계좌 복리 성과가 아니다.

실행 요청 예제·응답·데이터 정책·검증 방법은 [사용자 전략 백테스트 API](user-strategy-backtest.md)에 정리했다. 이 단계에는 빠져 있던 2단계 Java 명세·검증 구현도 포함한다.

**후속 범위:** 전략·결과의 DB 저장과 버전 이력은 4단계, LLM·웹 연결은 5단계, 차트·AI 설명·사용자 전략 비교와 전략별 페이퍼 실행은 이후 단계다. 이번 응답의 실행 스냅샷을 영구 이력 저장 완료로 해석하지 않는다. 14장의 전체 플랫폼 완료 점검표도 이 단계만으로 완료 처리하지 않는다.

## 17. 결과 차트와 AI 설명 진행 기록 (2026-09-14)

이전 장의 후속 범위는 각 기록 당시 상태다. 4단계 저장·버전 이력과 5단계 Codex·웹 연결 위에 6단계 결과 분석 화면과 실행별 설명 저장 기능을 추가한다.

- 실행 당시 저장된 캔들과 거래로 종가·체결점, 거래 수익률 누적 합계·낙폭 차트를 제공한다.
- 거래 번호로 진입·청산 근거를 연결하고 한국 시간 청산월 및 청산 사유별 거래 수익률을 집계한다.
- 기존 Codex 구독 연결로 설명 근거를 선택한다. 서버는 근거 ID·수치·거래 번호를 검증하고 확인 가능한 문장만 표시한다.
- 설명은 실행별로 생성 시각·모델·데이터 해시와 함께 저장한다. 조회 시 모델을 다시 호출하지 않으며 실패해도 기존 수치·거래 조회를 유지한다.
- 기존 엔진의 단순 합산·비용 미반영·비연율화 기준을 유지하고 화면에 표시한다. 계좌 수익률이나 시장 사건의 인과관계로 표현하지 않는다.

구체적인 API, 사용 방법과 검증 결과는 [결과 차트와 AI 설명](backtest-results-explanation.md)에 기록한다. 사용자 전략 비교와 전략별 모의매매는 각각 7·8단계 후속 범위다.

## 18. 저장 전략 비교 진행 기록 (2026-09-22)

사용자가 승인한 7단계 A안은 같은 유형의 저장 전략 2~6개를 공통 입력·동일 캔들 묶음으로 실행하고, 당시 버전·데이터·지표·원본 거래/판정 근거를 비교 전용 H2 스냅샷에 저장한다. 웹에서 전략 조건·수익률·낙폭·거래 수·성과 곡선과 비교 이력을 조회한다.

단일 종목은 기존 거래 단위 계산을 유지하며 자금·비용 입력을 거절한다. 포트폴리오·조합은 명시적인 초기자금·비용을 사용한다. 유형 간 비교와 단일 종목 계좌 모델 확장은 이번 범위에 포함하지 않는다. 세부 범위·사용법·검증은 [저장 전략 비교](strategy-comparison.md)를 따른다. 전략별 페이퍼 트레이딩은 8단계다.

## 19. 전략별 페이퍼 트레이딩 A 진행 기록 (2026-09-29)

단일 종목 저장 전략(형식 1·2)의 버전을 고정하고 국내 주식 한 종목에 독립 가상 계좌를 만드는 기능을 추가했다. 초기자금·매수 비중·비용·체결 방식을 명시하며, 공통 판정기로 일봉을 처리하고 실행 당시 입력·계좌·포지션·대기 주문·거래 근거를 H2에 보존한다.

웹에서 저장 버전 선택 → 시작 → 갱신·조회 → 신규 매수 중지로 연결한다. 중지 후 보유분은 기존 청산 조건으로 관리한다. 한국 날짜 기준 오늘 이전의 확정 일봉을 사용하므로 장중 실시간 체결 기능과 구분한다. 최초 판단 가능일은 생성일 다음 날짜다.

사용법과 실제 지원 범위는 [저장 전략 모의매매](strategy-paper-trading.md), 검증 결과는 [구현 기록](strategy-paper-trading-plan.md)을 따른다. 실제 시세 인증·운영 서버 적용·장기간 자동 실행 검증과 포트폴리오·조합 전략 모의매매는 완료 범위에 포함하지 않는다.

## 20. 통합 검증과 발표·시연 준비 (2026-09-30)

자연어 해석 → 서버 검증 → 전략 저장 → 실제 거래가 있는 백테스트 → 결과 분석 → 전략 비교 → 같은 ID·버전의 모의매매 시작·갱신·중지·재조회를 한 테스트로 연결했다. 고정 전략 JSON 2개와 합성 일봉 CSV를 테스트 리소스로 보관한다. AI 설명 실패 후 결과 보존, 모의매매 시작 재시도의 멱등성과 중복 계좌 거절도 이 연결 흐름에서 확인한다.

기존 테스트로 잘못된 프롬프트·데이터 부족·거래 없음·파일 H2 재시작·동시 갱신을 검증하고, 실제 HTTP·H2·브라우저 리허설과 전체 회귀·JAR 빌드를 `scripts/verify-stage9.ps1`로 재실행한다. 통과·제외 수와 증거 파일은 [통합 검증과 시연](integration-demo.md)의 검증 결과에 기록한다.

동일 문서에 9분 발표 진행안, 저장 필드·버전·실행 스냅샷에 대한 질의응답, 로컬 앱에서 읽기 전용으로 확인한 저장 전략 예시를 추가했다. README에도 실행 명령과 상세 문서 링크를 제공한다.

**완료 경계:** AI·시세 응답은 고정하고 테스트 DB를 사용한다. 실제 Codex·토스 연동 재검증, 운영 DB 변경·서버 배포, 장기 자동 실행, 발표 중 계속 켜 두는 별도 데모 서버는 포함하지 않는다. 모의매매는 첫 판단 가능일 전 과거 자료를 준비용으로만 사용하며 즉시 거래를 만드는 시연이 아니다.
