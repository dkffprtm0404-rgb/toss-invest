# 저장 전략 모의매매 — 8단계 A

단일 종목 저장 전략(형식 1·2)을 독립 가상 계좌로 실행한다. 저장 버전, 자금·비용, 입력 일봉, 포지션, 대기 주문, 거래와 평가액을 H2에 보존한다. 기존 점수제 모의매매는 그대로 유지한다.

## 화면 사용법

1. 투자 전략 화면에서 저장 전략과 버전을 선택한다.
2. **이 버전으로 모의매매**를 누른다. 계좌·모의매매 화면으로 이동한다.
3. 국내 종목 코드, 체결 방식, 초기자금, 매수 비중, 수수료·매도세·슬리피지를 모두 입력한다. 비용을 적용하지 않으면 0을 입력한다.
4. **모의매매 시작**을 누른다. 종목 정보 API에서 KOSPI/KOSDAQ·원화·주식 여부를 확인해야 시작할 수 있다.
5. **일봉 갱신 및 처리**로 수동 갱신하거나 자동 갱신을 기다린다. 실행 목록에서 계좌와 거래·일별 평가액·로그를 다시 조회한다.
6. **신규 매수 중지**는 대기 매수를 취소하고 신규 매수를 막는다. 보유분은 원래 전략의 청산 조건으로 관리한다. 청산 후 종료되며, 청산 조건이 없으면 계속 보유할 수 있다.

전략을 수정해도 실행 중인 버전은 바뀌지 않는다. 같은 전략·종목의 미종료 실행은 하나만 허용한다. 종료한 뒤 새 계좌를 만들 수 있다. 종료 이력 삭제는 저장 전략에 영향을 주지 않는다. 미종료 실행이 있으면 전략 삭제가 거절되고, 종료된 페이퍼 이력은 원 전략 삭제 후에도 보존한다.

## 일봉 반영 시점

장중 주문이 아닌 **확정 일봉을 이용한 가상 체결**이다. 한국 날짜 기준 오늘 이전 봉만 처리한다. 신호일, 체결 기준일, 실제 서버 반영 시각을 거래 기록에서 구분한다.

- 생성일 다음 날짜부터 매매 판단을 허용한다. 이전 일봉은 지표 준비에만 사용한다.
- 예: 9월 29일에 시작하면 9월 30일 봉부터 판단하며, 해당 봉은 10월 1일 이후 처리할 수 있다. 그날 데이터가 없으면 다음 실제 입력 봉을 기다린다.
- 당일 종가 방식은 해당 봉의 종가, 다음 일봉 시가 방식은 신호 후 다음 입력 봉의 시가에 슬리피지를 반영한다. 다음 시가 체결도 해당 봉이 확정된 뒤 기록한다.
- 시작 직후 거래가 없어도 실패를 뜻하지 않는다. 첫 판단 가능일, 마지막 처리 일봉, 지표 준비 부족·현금 부족·데이터 대기 상태를 확인한다.
- 최초 준비 데이터는 기존 시세 API에서 최대 15페이지·3000봉을 받는다. 이후 마지막 처리 날짜와 겹치는 구간까지 받아 연속성을 검사한다. 최대 보존 한도는 실행당 20000봉이다.
- 확정 표시가 없는 당일 봉, 미래 봉을 거래에 사용하지 않는다. 휴장·거래정지·누락을 임의로 구분하거나 가격을 채우지 않는다.
- 이미 보존한 가격이 수정되면 오류로 중단한다. 수정주가 변경·주식 분할에 따른 계좌 조정은 자동으로 수행하지 않는다.

자동 갱신은 서버 시작 60초 후부터 30분 간격으로 미종료 실행에 적용한다. `strategy.paper.scheduling-enabled=false`로 예약 작업을 끌 수 있다. 간격은 `strategy.paper.initial-delay-ms`, `strategy.paper.delay-ms`로 설정한다. 수동 갱신은 예약 작업 사용 여부와 관계없이 제공한다.

## 계좌와 전략 판단

매수 예산은 가용 현금 × 매수 비중이다. 슬리피지·수수료를 포함한 금액으로 살 수 있는 정수 수량을 계산한다. 추가 매수·부분 매도는 없고 청산은 전량이다. 손절 등 가격 판단의 매수가는 슬리피지가 포함된 가상 체결가이며 수수료·세금은 계좌 손익에 반영한다.

계좌 수익률은 `(현금 + 보유 평가액) / 초기자금 - 1`, 최대 낙폭은 초기자금을 포함한 평가자산 최고값 대비 하락 비율이다. 미실현손익은 매수 수수료를 포함한 원가 대비 평가액 차이이며 아직 발생하지 않은 매도 비용은 차감하지 않는다. 누적 비용 표시는 수수료·세금 합계이며 슬리피지는 체결 가격에 반영한다.

기존 단일 종목 백테스트의 거래 수익률 합계·거래 낙폭·샤프와 계좌 지표를 혼동하지 않는다. 비용 0과 같은 입력 데이터에서는 공통 `StrategyEvaluator`로 동일한 위험 조건과 체결 가격을 사용한다. 날짜가 비어 있는 구간은 추가하지 않으며 보유기간은 매수 봉을 0으로 한 일봉 수다.

## API

시작 요청 예제의 숫자는 사용자가 선택한 예시이며 자동 기본값이 아니다.

```json
{
  "strategyId": 1,
  "version": 1,
  "symbol": "005930",
  "executionMode": "NEXT_DAY_OPEN",
  "initialCapital": 1000000,
  "allocationRate": 0.5,
  "commissionRate": 0.00015,
  "taxRate": 0,
  "slippageRate": 0,
  "requestId": "paper-example-20260929"
}
```

- `POST /api/strategy-paper/runs`: 시작. 같은 요청 식별자와 같은 입력의 재시도는 기존 실행을 반환한다. 금액의 소수 표기 차이는 같은 값으로 처리한다.
- `GET /api/strategy-paper/runs?page=0&size=20`: 실행 목록. `strategyId`, `symbol`, `status` 필터를 지원한다.
- `GET /api/strategy-paper/runs/{id}`: 실행 당시 전략·설정·계좌와 최근 이력 요약.
- `POST /api/strategy-paper/runs/{id}/refresh`: 수집과 미처리 일봉 반영.
- `POST /api/strategy-paper/runs/{id}/stop`: 신규 매수 중지와 청산 관리.
- `GET /api/strategy-paper/runs/{id}/trades`, `/equity`, `/logs`: 최신순 페이지 조회. `page >= 0`, `1 <= size <= 100`.
- `DELETE /api/strategy-paper/runs/{id}`: 종료된 실행만 삭제.

계좌 상태는 `RUNNING`, `STOPPING`, `STOPPED`다. 데이터 상태는 `WAITING_DATA`, `READY`, `INSUFFICIENT_DATA`, `INSUFFICIENT_CASH`, `INVALID_DATA`와 아래 시세 오류로 별도 제공한다. 갱신 응답 HTTP 200은 새 거래가 생겼다는 의미가 아니다. 데이터 상태와 로그를 확인한다. 시세 실패 시 마지막 저장 계좌를 유지하며 실패 이유를 로그로 남긴다.

- `MARKET_REQUEST_REJECTED`: 날짜 등 요청 파라미터 거절(401·403·429를 제외한 HTTP 4xx). 동일 입력을 반복하기보다 서버 요청 형식을 확인한다.
- `MARKET_AUTH_FAILED`: HTTP 401·403. 시세 API 인증·접근 권한을 확인한다.
- `MARKET_RATE_LIMITED`: HTTP 429. 잠시 후 갱신한다.
- `MARKET_UNAVAILABLE`: 네트워크 연결 실패 또는 시세 제공업체 HTTP 5xx. 연결 상태·제공업체 상태를 확인한다.
- `MARKET_ERROR`: 그 외 응답 처리 오류. 서버 로그의 실행 ID·종목·예외 종류를 확인한다.

화면의 갱신 안내와 계좌 상세에는 최근 상태에 해당하는 원인·HTTP 상태·다음 조치를 표시한다. 인증 토큰과 제공업체 응답 원문은 노출하지 않는다. 정상 수신 후 매매 시작일 전 준비 데이터만 받은 경우에도 과거 실패 상태를 해제하고 `WAITING_DATA`로 전환한다. 이전 실패 로그는 기록으로 보존한다.

잘못된 입력은 400, 없는 실행·버전은 404, 중복 실행·상태 충돌은 409, 시작 시 종목 조회 연결 실패는 503이다. 시작 시 국내 주식 확인을 통과하지 못하면 400으로 거절한다.

## 영속 구조와 변경 파일

새 `strategy_paper_run` 테이블에 실행별 입력·전략·전체 계좌 상태를 JSON으로 보존한다. 상태에는 사용한 일봉, 거래, 평가액과 로그가 포함된다. 실행 행의 DB 잠금과 원자적 체크포인트 갱신으로 처리 위치와 잔고를 함께 저장한다. `requestId`와 미종료 실행 키에는 DB 유일 제약을 둔다. 일봉 날짜 중복·수정은 엔진에서 검사한다. 데이터 출처와 SHA-256도 저장한다.

설계 초안의 별도 일봉·거래 테이블 대신 실행 단위 JSON 체크포인트를 사용했다. 단일 종목 초기 범위에서 원자적 복구를 간단히 보장하기 위한 선택이다. 조회 요약에서는 일봉 원문을 제외하고 최근 거래·평가액·로그만 반환하며 전체 거래 이력은 페이지 API로 제공한다.

- `strategypaper/`: `PaperDefinition`, `PaperState`, `StrategyPaperEngine`, `PaperMarketData`, `PaperRunEntity`, `PaperRunRepository`, `StrategyPaperService`, `StrategyPaperController`, `StrategyPaperScheduler`, `PaperDeletionGuard`, `PaperConflict` 추가.
- `strategy/StrategyDeletionGuard.java` 추가, `SavedStrategyService.java` 삭제 보호와 `StrategyApiErrors.java` 오류 응답 확장.
- `static/js/strategy-paper.js`, `static/css/strategy-paper.css` 추가, `index.html`과 `strategy-workbench.js` 연결.
- 테스트: `StrategyPaperEngineTests`, `StrategyPaperApiTests`, `StrategyPaperPersistenceTests`, `PaperMarketDataTests`, `StrategyPaperWebWorkflowTests` 및 `strategy-paper.browser.cjs`, `strategy-paper.server.cjs`.
- 문서: 설계·구현 기록·사용 안내와 기획서 진행 기록.

## 검증과 한계

검증 명령과 최종 결과는 [구현 기록](strategy-paper-trading-plan.md)에 기록한다. 고정 데이터로 계좌 분리, 위험 정책의 백테스트 일치, 중복 호출, 비용, 중지, 파일 H2 재시작, 이력 보존을 확인한다. 실제 HTTP·H2·브라우저 통합 테스트에서는 시세·AI 제공업체만 대체한다.

2026-09-29 실제 토스 시세의 일봉 다음 페이지 조회를 검증했다. `before` 시간대의 `+`를 수동 인코딩한 뒤 WebClient가 다시 인코딩하여 `%252B`가 전송되는 오류를 수정했다. 같은 요청이 수정 전 HTTP 400 `before/typeMismatch`, 수정 후 200·일봉 200개로 바뀌었다. 개발 서버 자동 반영 후 기존 실행 #2에 일봉 2985개가 보존됐고 마지막 처리일은 2026-09-28이다. 화면 수동 재갱신에서도 중복 저장 없이 `WAITING_DATA`를 확인했다.

새 실행은 생성일 다음 날짜 이후 봉을 기다리므로 이번 실환경 확인에서 가상 매수·매도 체결을 만들지는 않았다. 장기간 예약 실행과 포트폴리오·조합 전략 페이퍼 실행은 이번 검증 범위에 포함하지 않는다. 자동 재시작을 쓰지 않는 서버에서는 빌드·재시작 후 브라우저를 새로고침해야 한다.
